# 给新同学的 RAG 入门介绍

> 写在前面：这份文档不需要你有任何 AI/机器学习背景。我们会先用几个生活化的比喻把"RAG 是什么、为什么要学它"讲清楚，再带你看一眼接下来几周大概会学到什么。目标不是让你现在就看懂所有技术细节，而是让你带着一张"地图"开始学习——知道每一块内容在整体里处于什么位置、解决什么问题。

## 一句话说清楚：RAG 是什么

RAG 全称 **Retrieval-Augmented Generation**，中文常翻成"检索增强生成"。

听起来很技术，但可以用一个很简单的比喻理解：**让 AI 回答问题之前，先给它一本可以翻阅的书，而不是只让它凭脑子里记住的东西回答。**

普通的大语言模型（比如你平时用的 ChatGPT、Claude）在回答问题时，靠的是训练时"记"进参数里的知识——就像一个博览群书但已经很久没读新书的人，凭记忆回答你。这有两个明显的问题：

- 它不知道你公司内部的资料、你昨天刚发生的事、或者训练之后才出现的新信息。
- 它偶尔会"记错"或者干脆编一个听起来很像真的答案（这就是常说的"幻觉"）。

RAG 做的事情很朴素：**在 AI 回答之前，先去一堆指定的文档里搜出跟问题相关的内容，把这些内容也交给 AI，让它照着这些"证据"来回答**，而不是单纯凭记忆瞎猜。

```
用户提问
  → 先去资料库里找相关的内容片段
  → 把问题 + 找到的内容片段一起交给 AI
  → AI 基于这些内容片段生成答案
```

简单说：**普通模型 = 改变模型脑子里记住的东西；RAG = 回答时额外给它一批参考资料。**

需要提醒一句：RAG 不是"上了保险"就万无一失。系统依然可能找错资料、漏掉关键内容，或者 AI 说了一些资料里根本没支持的话——这些恰恰是这门课接下来要一步步解决的问题。

## 为什么现在模型上下文窗口越来越大了，RAG 还是不会消失

现在的模型能一次性"塞进去"几十万甚至上百万字，你可能会问：既然能塞这么多，为什么还需要"先搜索再回答"这一步？

课程里有一句话很好地回答了这个问题：

> 上下文窗口不是文件柜，而是一张书桌。你仍然需要图书馆。

也就是说：

- **上下文窗口**只是模型当前"摊在桌面上"的一小块工作空间，装的是这一刻正在处理的东西。
- 真正的**知识库/文档库**是图书馆——庞大、持续更新、包含各种权限和新鲜度不一的资料。
- 就算书桌再大，它也不会自己跑去图书馆，帮你挑出"最相关、最新、你有权限看、而且可信"的那几本书摆上来。
- **RAG 干的正是这件事**：它是图书馆和书桌之间那位懂行的图书管理员，负责搜索、筛选，把真正有用的证据递到模型面前。

所以哪怕窗口再大，"该给模型看哪些东西"这个决策依然需要一套机制去做——这就是 RAG 存在的意义，也是这门课要系统教的内容。

## RAG 和"直接调教模型"（微调）有什么不同

有时候大家会问："为什么不直接把公司的知识'训练'进模型里？"——这就是微调（fine-tuning）。两者不是竞争关系，是解决不同问题的工具：

| 场景 | RAG 更合适 | 微调更合适 |
|---|---|---|
| 信息经常变化（比如价格、政策、最新数据） | ✅ 改一下资料库就行 | 每次都要重新训练，成本高 |
| 需要说清楚"这个答案是从哪来的" | ✅ 天然可以指出来源 | 知识被"揉"进了参数里，说不清来源 |
| 涉及私有/敏感文档 | ✅ 按需检索，权限好控制 | 训练时接触过的数据，删除和隐私更麻烦 |
| 想让模型换一种说话风格或行为方式 | 能力有限 | ✅ 更适合 |

一句话总结：**RAG 管"模型知道什么"，微调更适合管"模型怎么说话、怎么做事"。** 这两者经常会被组合使用。

## 这门课打算怎么教：一条流水线，七个阶段

课程不是把 RAG 当成一堆孤立的技巧（"用个向量数据库""调个 embedding 模型"）来讲，而是把它当成一条完整的**端到端流水线**：

```
原始文档 → 摄取 → 检索 → 增强 → 可扩展架构 → 安全与可信 → 评估 → 可衡量、可信的答案
```

接下来几周大致会按这条线展开，每一站解决一个具体问题。给不熟悉技术的同学翻译一下每一站在干什么：

**1. 基础：机器怎么"理解"文字**
模型不是真的"读懂"文字，而是把文字变成一串数字（叫 embedding），这串数字在一个抽象空间里的"位置"大致代表了它的意思——意思相近的内容，位置也相近。后面几乎所有环节都建立在这一层地基上。

**2. 摄取：怎么把一堆文档切成能被搜索的小块**
一份很长的文档不能整篇丢给检索系统，需要先切成一个个小片段（chunk）。这一步的切法很关键——课程里叫它"第一次不可逆的切割"：如果切的时候把该保留的上下文弄丢了，后面不管用多好的技术都补不回来。

**3. 检索：怎么从一堆文档里，把真正相关的几段挑出来**
既要能匹配"用户说的原话"（比如人名、编号这种精确信息），也要能匹配"用户想表达的意思"（哪怕用词完全不一样）。这一步还会讲到怎么把用户含糊、口语化的提问，"翻译"成检索系统更容易理解的查询。

**4. 增强：怎么让检索到的证据质量更高**
比如提前把文档"提炼"成摘要、问答对、原子事实等多种形式，方便不同风格的提问都能命中；再比如像显微镜（看细节）、变焦镜头（在细节和摘要之间自由切换）、望远镜（看清整个语料库的结构和关系）这样，针对不同类型的问题选择不同的"看法"。

**5. 可扩展架构：什么规模用什么复杂度**
不是资料越多、技术越花哨越好——课程强调"先搭一个最简单能跑的系统，观察它哪里失败，再针对性地加东西"，而不是一上来就堆砌所有技术。

**6. 安全与可信：怎么防止 AI 乱说话**
一部分机制在问题进来时就把危险或越权的请求挡掉（护栏）；另一部分机制在答案生成后核查——这句话是不是真的有证据支持，而不是模型自信地编出来的。

**7. 评估：怎么知道系统做得好不好**
检索得好不代表回答得好，回答得好听不代表真的有证据支撑——这一步会分别衡量流水线的每一段，而不是只看一个笼统的总分。

## 给刚开始学的你：几个心态建议

- **不用一开始就看懂所有术语。** embedding、chunk、reranker 这些词现在听着陌生很正常，跟着流水线的顺序学，每一站会把上一站用到的概念讲透。
- **多记比喻,少死记术语。** 这门课本身也很依赖比喻(书桌与图书馆、翻译官、显微镜与望远镜)——先建立直觉,术语会自然而然地"挂"上去。
- **RAG 不是一个"装上就完事"的黑盒。** 它更像一整套需要持续调优、持续验证的工程实践——这也是为什么课程花了大篇幅讲"怎么评估、怎么判断该不该加某个组件"，而不是只教"怎么搭一个能跑的 demo"。
