# KV Cache 与 Prefix Caching：缓存的最底两层

Week 12（2026-08-29）课堂追问整理。对应 [`week-12.zh.md`](week-12.zh.md) 第四节「缓存可以放在哪一层」的下面两行展开。

> **一句话**：KV cache 是让生成**跑得起来**；prefix caching 是让重复的开头**不白算**；语义缓存是**赌整个问题都不用算**。风险沿这条线一路上升。

---

## 第一部分：KV Cache

### 一、是什么

先看**不缓存会怎样**。模型生成是一个 token 一个 token 吐的：

```text
输入 5000 tokens → 生成第 1 个词 → 生成第 2 个词 → …
```

生成第 2 个词时，模型需要"看"前面 5001 个 token。**如果什么都不存，它得把这 5001 个 token 从头再前向传播一遍。**生成第 3 个词，再来 5002 个。

但注意力机制里，每个 token 在每一层都会算出两个向量：

- **K（Key）** —— "我是什么，可以被怎么检索"
- **V（Value）** —— "如果检索到我，我贡献什么内容"

关键在于：**因为注意力是因果的，一个 token 的 K/V 只取决于它自己和它前面的 token——后面来了什么，都不会改变它。**

所以这些 K/V **算一次就永远有效**。存下来，就叫 KV cache。

```text
生成第 1 个词：算 5000 个 token 的 K/V   → 存进 cache
生成第 2 个词：只算新增那 1 个 token 的 K/V → 追加进 cache
生成第 3 个词：只算新增那 1 个
…
```

> ⚠️ KV cache **不是**"缓存答案"，是缓存**计算的中间状态**。它和语义缓存完全不在一个层次上。

### 二、好处：从平方降到线性

具体请求算账 —— 5000 token 输入、生成 500 token：

| | 总计算量（token 前向次数） |
| --- | --- |
| 无 KV cache | 5000 + 5001 + … + 5500 ≈ **262 万** |
| 有 KV cache | 5000（prefill）+ 500（每步 1 个）= **5500** |

**差约 480 倍。**本质是把 $O(n^2)$ 降到 $O(n)$。

这不是"优化"，是**可行性前提**——没有 KV cache，自回归生成在工程上根本跑不起来。所有推理框架**默认全开**，不是可选项。

### 三、代价与风险

#### ① 显存 —— 主要代价

KV cache 住在显存里，**每个 token、每一层都要存**：

$$\text{大小} = 2 \times L_{\text{层数}} \times H_{\text{KV头}} \times d_{\text{头维度}} \times n_{\text{tokens}} \times \text{字节数}$$

以 Llama-3-70B（80 层、8 个 KV 头、head\_dim 128、fp16）为例：

```text
每个 token = 2 × 80 × 8 × 128 × 2 字节 = 327,680 字节 ≈ 320 KB
```

| 场景 | KV cache 占用 |
| --- | --- |
| 单请求 8K 上下文 | 320KB × 8192 ≈ **2.6 GB** |
| 32 个并发请求 | ≈ **84 GB** |
| 单请求 128K 上下文 | ≈ **42 GB** |

一张 H100 只有 80GB，70B 模型权重本身就要多卡。**剩下的显存决定能并发跑几个请求——也就是决定吞吐量。**

> 在生产推理里，**KV cache 显存几乎总是吞吐量的瓶颈**，比算力更早撞墙。
>
> 这就是 GQA / MQA / MLA 这些架构改进存在的理由——它们就是为压缩 KV cache 设计的。上面 70B 的「8 个 KV 头」就是 GQA 的效果；若是标准 MHA 要 64 个头，占用 **×8**。

#### ② 碎片化

早期实现给每个请求按最大长度预分配连续显存 → 实际只用一小半，浪费 60~80%。vLLM 的 **PagedAttention** 借用操作系统分页思路解决（这也是 vLLM 出名的原因）。

#### ③ 量化会改变输出

为省显存可把 KV cache 从 fp16 压到 fp8 / int4。这是**唯一一种会让输出发生变化**的情况——精度损失让生成结果轻微漂移。开不开是个权衡。

#### ④ 跨请求共享时的安全风险 ⚠️

**单个请求内部用 KV cache：零风险**，数学上和重算完全等价。

但一旦**跨请求共享前缀**（即 prefix caching），就开了一个侧信道：

```text
攻击者发一个 prompt：「[某公司 system prompt] 关于收购 XX 公司的尽调…」
   → 首字延迟 30ms   → 说明这个前缀在缓存里 → 别人刚问过这件事 ⚠️
   → 首字延迟 800ms  → 说明没人问过
```

**攻击者不需要拿到任何内容，只靠计时就能推断「有没有人问过某个问题」。**在多租户共享部署里，这可以泄露商业机密（谁在做什么并购、谁在查哪个客户）。

防御方向：按租户隔离缓存池、给缓存命中加随机延迟、对敏感前缀禁用共享。

> 📌 这条大概率就是 **INTERLUDE「The Adversary」**要讲的东西之一，课上留意验证。

## 第二部分：Prefix Caching

### 一、是什么

模型处理请求分两阶段：

```text
① Prefill（预填充）：把整个 prompt 读一遍，为每个 token 算 K/V
                     成本 ∝ prompt 长度，一次性大计算
② Decode（解码）：   基于这些 K/V 逐个吐出新 token
                     成本 ∝ 输出长度
```

RAG 的 prompt 通常很长（system prompt + 5 个 chunk + 历史），输出却很短。**所以 prefill 常是大头。**

利用同一个因果性质：如果两个请求的**开头一模一样**，那段开头的 K/V 就是**逐比特相同**的 → 存下来跨请求复用，跳过这部分 prefill。

### 二、例子

典型 RAG prompt：

```text
┌─────────────────────────────────────┐
│ [system] 你是企业知识助手，回答须…    │  1200 tokens  ← 每次都一样
│ [few-shot] 示例1… 示例2… 示例3…      │  2000 tokens  ← 每次都一样
│ [工具定义] search(), lookup()…       │   800 tokens  ← 每次都一样
├─────────────────────────────────────┤  ← 前缀到此为止：4000 tokens
│ [检索结果] chunk1… chunk5…           │  1500 tokens  ← 每次都变
│ [用户问题] 报销流程是什么？           │    20 tokens  ← 每次都变
└─────────────────────────────────────┘
```

- 无 prefix caching：每次 prefill **5520** tokens
- 有 prefix caching：前 4000 命中，只 prefill **1520** tokens

**省掉 72% 的 prefill。**首字延迟（TTFT）跟着大幅下降——prefill 就是首字前的那段等待。

### 三、一字之差，全盘皆输

精确匹配的代价：**前缀里改一个字符，该位置往后的 K/V 全部作废。**

最常见的反模式——把易变内容放在 prompt 开头：

```text
❌ "当前时间：2026-08-29 12:47:33。你是企业知识助手…"
        ↑ 每次请求都不同 → 从第 5 个 token 起全部 miss，命中率 0%

✅ "你是企业知识助手…（4000 tokens 固定内容）…
    当前时间：2026-08-29 12:47:33
    用户问题：…"
        ↑ 易变内容挪到末尾 → 前 4000 稳定命中
```

同类的坑：用户名、session ID、随机排序的工具列表、每次重新生成的 few-shot 示例。

> **设计原则：prompt 按「稳定度」从高到低排列。越不变的越靠前。**

### 四、实践要点

- 主流推理框架（vLLM、SGLang）和商用 API（Anthropic、OpenAI、Google）都支持，有的自动、有的要显式标记缓存断点
- 缓存 K/V 占显存，所以有 TTL 和容量上限，冷了会被驱逐
- 计费上通常「写入略贵、读取便宜很多」——**具体倍率和 TTL 各家不同且会变，实际要用时查当前文档**

## 第三部分：KV-cache reuse（比 prefix caching 更激进的变体）

讲义 p.7 的象限图里，`prefix caching` 右边还有一个 **KV-cache reuse — chunk states, repaired attention**（分块状态，修补过的注意力）。这是前面没写到的一层。

### 差别：复用的位置

| | prefix caching | KV-cache reuse |
| --- | --- | --- |
| 复用的位置 | **只能是开头** | **任意位置的 chunk** |
| 为什么受限 | 因果注意力要求前缀逐 token 一致 | 主动打破这个限制 |
| 代价 | 无 | **需要"修补"注意力** |
| 精确性 | 完全精确 | **轻微近似** |

### 为什么需要"修补"

RAG 的痛点：检索到的 5 个 chunk **每次组合和顺序都不同**，所以永远不构成稳定前缀，prefix caching 完全用不上——而 chunk 恰恰是 prompt 里最长的部分。

KV-cache reuse 想解决这个：**给每个 chunk 单独预存一份 K/V，用到时直接拼装。**

但有个问题——一个 chunk 原来在位置 3000 算 K/V 时"看到"的上文，和它现在被放到位置 1500 时的上文**不一样**。直接拿来用会有偏差。

于是**重算一小部分注意力来修补**（选择性地重算跨 chunk 边界那些最关键的 token），把偏差压到可接受范围。

```text
prefix caching：  [固定前缀]|[变动部分]        ← 只能在这条竖线左边复用
KV-cache reuse：  [chunkA][chunkC][chunkB][query]
                     ↑       ↑       ↑
                  各自预存的 K/V 拼起来 + 修补边界
```

### 所以它在象限图上靠右一点

因为**引入了近似**——不再是"数学上完全等价"，而是"近似等价，误差可控"。这类技术（CacheBlend 一系）也正是配套专著叫 **CacheCraft** 的原因之一。

> ⚠️ 注意分寸：它仍然**远比语义缓存安全**——语义缓存是"赌这是同一个问题"，KV-cache reuse 只是"这段文本的表示算得略有偏差"。**前者可能答错，后者只是答得略糙。**

## 四层全景（讲义 p.7 象限图）

讲义用两个轴把整个缓存家族排开了：

```text
复用答案 ↑
         │  （空象限）              ★ semantic cache
         │  = 那就是个数据库           完成的答案，近似匹配
         │                          ← 家族里唯一会出错的成员
         │  embedding cache
         │  文本→向量，精确 key
         │
复用计算 │  prefix caching      KV-cache reuse
         │  供应商 KV，省 ~90%   分块状态，修补过的注意力
         └────────────────────────────────────────→
         精确匹配                        近似匹配
```

- **纵轴**：复用的是什么（计算 → 答案）
- **横轴**：匹配方式（精确 → 近似）
- **语义缓存孤零零在右上角**——同时把两个维度推到极端，所以它是唯一会出错的那个

详见 [`prologue.zh.md`](prologue.zh.md) p.7 一节。

## 三层对比（本篇重点）

| | KV cache（单请求内） | Prefix caching（跨请求） | 语义缓存 |
| --- | --- | --- | --- |
| 缓存什么 | K/V 中间状态 | 同左，但跨请求复用 | 最终答案 |
| 匹配方式 | 无需匹配 | **精确**逐 token 前缀 | **模糊**语义 |
| 省什么 | 生成过程的重复计算 | prefill | 检索 + 生成，全省 |
| 会不会答错 | **不会** | **不会** | **会** |
| 主要风险 | 显存 | 计时侧信道 | false hit |
| 谁负责 | 推理框架，默认开 | 框架/API，需配合 prompt 设计 | 你自己实现 |

**Prefix caching 和语义缓存是完全相反的东西**：一个精确匹配、零风险、框架自动；一个模糊匹配、有 false hit、要自己实现 γ/τ/p\*（见 [`sigmoid-decision.zh.md`](sigmoid-decision.zh.md)）。

> Prefix caching **不需要 γ、不需要 τ、不需要 p\***——复用 K/V 和重算数学上完全等价，输出一模一样。**没有决策，只有省钱。**这就是它排在上线顺序最前面的原因。

## 留存句

- **KV cache 不是优化，是可行性前提**——没有它自回归生成跑不起来
- **KV cache 显存是生产推理的真瓶颈**，比算力更早撞墙；GQA/MQA/MLA 都是为压它而生
- **prompt 按稳定度从高到低排列**——把时间戳放开头 = 亲手把命中率清零
- **单请求内零风险，跨请求共享才有侧信道**——计时就能泄露"谁问过什么"
